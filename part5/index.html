    第五篇：多智能体与环境交互系统

    Multi-Agent Systems and Environment Interaction

    篇页数预算： 130 个等效出版页，含四章的图表、案例、练习和参考文献；本导读在篇级统稿时合并核算。主责学生 E，正式作者信息随全书确认。

    从一个助手到一个有责任边界的团队

    政策研究与工单助手需要先查明适用规则，再准备行动，最后核验实际结果。任务较小时，一个助手配合明确工具就可能足够。随着证据和工作量增加，研究、执行与核验可以由不同成员承担，但分工也带来新问题：研究者退出后谁接手，旧消息是否仍有效，成员一致时谁检查证据，以及页面变化后是否还能按原计划点击。

    本篇依次回答“谁负责、消息怎样生效、判断依据是什么、行动如何跟随环境变化”。增加角色数量只改变组织形式；只有职责、协议、判断和反馈共同受到约束，团队才能形成可检查的交付。读者应始终保留一个单体基线，比较新增协调工作是否值得，而不是从多智能体必然更优的前提出发。

    四章沿用原创虚构政策和模拟工单，不对应真实企业制度。资格判断、主管批准、工具写入许可和业务完成是四个不同条件。某项申请符合政策，不表示执行者自动得到提交权限；消息已送达，也不表示工单已经创建。整篇以这些边界组织概念和实践。

    章节与能力地图

    章节 预算 读完应能完成的工作 交给下一章的产物
    Ch18 多智能体角色与组织结构 31 页 比较单体、主管和点对点结构，写清角色权限、唯一最终责任和委派上限 角色契约、最终负责者、根预算与拆分依据
    Ch19 多智能体通信与协调 34 页 定义领取、租约、候选提交、核验、去重和接管，解释重复、迟到和未知结果 可校验消息、状态与事件、候选关联和终态
    Ch20 集体推理、辩论与协商 30 页 对照投票与证据裁决，保留有效反证，分别评价正确性、共识和成本 主张证据矩阵、分歧处理、交付结论或未决事项
    Ch21 智能体感知与环境交互 35 页 区分状态与观测，建立有时效和版本的行动闭环，处理未知、重观测、停止与交接 环境卡、动作及反馈记录、独立后置验收和接管材料

    能力之间存在依赖。没有 Ch18 的责任划分，Ch19 的接管就缺少最终接受者；没有 Ch19 的版本与候选关联，Ch20 的裁判可能审核已经失效的答案；没有 Ch20 的证据检查，Ch21 的闭环可能高效执行错误判断；没有 Ch21 的实际反馈，前三章的交付又可能只停留在计划和文字上。

    学习前宜了解 Ch09 任务规划、Ch12 行动执行 和 Ch13 轨迹与恢复。需要证据检索时回到 Ch16；需要会话与事件持久化时接入 Ch23。本篇说明协作与环境契约，第九篇说明如何运行、测试和交付。

    贯穿案例与输入输出接口

    贯穿任务从“给出政策判断”逐步扩展为“有证据地交付并核验模拟工单”。每一步都保留任务修订、输入版本和责任人；发生变化时，接收方重新判断旧产物是否仍可使用。任务更新不等于新建任务，恢复也不自动重置预算或业务操作标识。

    接口 提供与消费关系 最小内容及接受条件 本地实现位置
    角色契约 Ch18 提供，Ch19/20 及运行时消费 输入、权限、输出、验收者、退出条件；每个根任务只有一个最终负责者 fixtures/study/role_contracts.json
    协调消息 Ch19 提供，研究/执行/核验成员消费 任务与父任务、消息、修订、分配代次、发送方、候选、租约和截止；身份由可信边界提供 fixtures/study/message_schema.json、coordination.py
    候选与证据 研究成员提供，核验者/裁判消费 内容摘要、政策版本、事实范围和反证；结果与当前任务及候选绑定 project2.py、debate_study.py
    根预算与终态 协调者提供，全部角色消费 授权/消息上限、截止、完成/取消/升级；成员退出不转移最终责任 study_manifest.json、协调队列预算表
    环境适配 Ch21 定义，行动与运行时消费 observe/act/query/reset，episode、依据版本、采集时刻、动作标识、可查询反馈 environment_study.py、环境卡
    业务验收 独立核验者提供，最终负责者消费 实际字段、唯一作用、拒绝/未知的证据；执行者自报不能替代外部读取 project2.inspect_task、环境 score()

    表中工程路径均相对于 examples/ch36/，模块文件位于 src/book_reference/。这是可运行的本地教学接口版本，尚待 C、D、F 消费者确认后并入团队公共模式；章节与项目复用同一实现，不另抄一套 schema。队列的受信本地进程身份不提供真实网络认证，不能把消息中的角色名当作授权凭证。

    建议阅读与实践路径

    第一次学习可按 Ch18→Ch21 顺读：先为单个任务说明分工收益，再增加通信故障，然后检查意见与证据，最后让动作接受环境反馈。做项目时可以从一个最小端到端任务开始，逐项增加这些约束；不要等所有模块完成后才首次检查整体任务。

    偏协议的读者可先读 Ch19，再到 Ch36 看持久化与恢复，到 Ch37 看独立断言。偏判断与评估的读者可结合 Ch20 和 Ch26；偏交互与运行时的读者可结合 Ch21 和 Ch22—25。部署条件和生命周期验收集中见 附录 D。

    完整工程统一在第九篇维护。从仓库根目录运行以下命令，输出目录须使用尚不存在的新名称：

    uv sync --project examples/ch36 --python 3.12 --locked
uv run --project examples/ch36 --python 3.12 --locked python examples/ch36/run_study.py all --output outputs/student-e-first
uv run --python 3.12 pytest

    运行包含本地 PRJ-2、Ch19 协调故障、Ch20 脚本模型对照、Ch21 两环境对照和附录 D 的配置发布演练。报告与原始事件位于输出目录，各实验保留独立任务 ID、分母及适用范围。Ch20 的脚本审查按公开规则纠错，不能据其结果推断真实语言模型的能力差异；Ch21 的模拟保护也不能证明真实浏览器或机器人具有相同原子性。

    篇末综合练习：交付一个可接管的协作任务

    以 T-DEMO-01 为起点，完成研究、执行和核验三角色的模拟工单任务。材料限于本地原创政策与模拟服务，不接真实企业系统。先说明该任务采用单体是否已经足够，再说明三角色版本多做了什么，以及这些工作产生了哪些额外成本。

    提交一份角色契约和接口版本清单，注明最终负责者；画出正常任务与提交后失联的事件次序；运行 PRJ-2 并从服务数据库独立核对工单字段、唯一创建事件和批准范围。随后加入一条迟到消息，解释它应被拒绝还是重放原回执，并保存实际原因。最后使用 Q01 检查政策版本分歧，使用 A02 或 B05 检查观测更新，把判断错误、通信错误和环境变化分别定位。

    交付包括 README、输入及预期、运行命令、原始事件、结果表、失败定位、分歧/接管记录和限制。若某条路径未执行，明确列为未执行，不用设计图代替结果。每份报告同时列成功与非成功任务；取消、升级和保护性停止不得被合并为业务成功。

    评分维度 分值 可检查的依据
    分工与最终责任 15 单体基线、角色权限及唯一收口者，收益和额外成本均说明
    通信与恢复 25 租约、重复、旧代次、未知结果和中断恢复有事件证据
    判断与证据 20 适用政策、独立答案、少数反证与未决处理可回查
    环境反馈与停止 20 观测时效、版本和实际后置条件清楚，停止不冒充完成
    复现与报告 20 新目录可运行、源码/数据可定位、分母与证据类型明确

    参考验收应看到：基础任务恰有一张金额 250 的工单；执行者提交后中断，恢复仍使用同一个操作标识；Q01 在当前规则下需要主管批准；A02 的旧定位不能造成错误作用，B05 的失败移动不能被记成位置已前进。允许基于边界清楚的其他实现，但任何“通过”都须能回到独立状态或原始事件，不能只给最终文字。
